# Federalism application guidance

This private repository owns the Federalism argument, political vocabulary,
institutional models, authored readings and manuscript. The public
[Blake repository](https://github.com/docxology/blake) owns corpus custody and
generic methods. Extend a shared method upstream; keep the question, domain
policy and interpretation here.

## Start and choose the relevant contract

1. Read [project status](docs/PROJECT_STATUS.md) for completed engineering,
   current delivery and bounded next work. Use that file as the single task
   index; the [research program](docs/research-program.md) explains scholarly
   acceptance criteria rather than a second implementation backlog.
2. For source or dependency work, read [shared methods](docs/shared-methods.md),
   then inspect `pyproject.toml`, `uv.lock` and `research/verification.json`.
   The installed SDK pin and the historical corpus producer identify different
   objects. Preserve the earlier corpus and analysis receipts when qualifying
   a new software dependency.
3. For manuscript or figure work, read the [authoring conventions](docs/style-guide.md)
   and [native render guide](docs/manuscript/README.md). The current paper is
   [Blakean_Federalism.pdf](Blakean_Federalism.pdf); its recorded producer and
   acceptance scope remain attached to those exact bytes.
4. For new source intake, import or corpus changes, read [privacy and custody](PRIVACY.md)
   and `research/corpus-pin.json` before choosing a new input/output epoch.

For a contextual workload, read [request-pinned planning](docs/research/review-planning.md)
and its exact request/source/decision pins. Shared ranking and batch custody
belong upstream; do not conflate this workflow with institutional standing.

For the timing atlas, read [its exact domain contract](docs/research/review-timing-atlas.md).
Keep the two slices and their shared configurations explicit, assess each person
separately, and distinguish zero uncovered time from the four unassessed practical
premises. Reuse public interval algebra; filing activation, duties and clock policy
belong in this application.

For the adverse review study or source variants, read
[review under pressure](docs/research/review-pressure-20261029.md) and the dated
collation before changing its cases, figure or claims. Keep this new family
separate from the fixed-duty order on the original fourteen procedures.

- Use GitVault's supported repository lease for source changes, project gates,
  commits and pushes. Verify the SSD mount, both Python prefixes and external
  temporary/cache bindings. Follow the vault's operating contract; keep one
  canonical copy and preserve other owners' working files and held locks.
- Run the environment and verification commands in [README.md](README.md).
  Use real files and real CLI/refusal controls. Read separate application and
  tool coverage totals; a combined headline does not establish both floors.
- Current unpublished 1.0.0 software selects Blake 0.7.0 at Git
  `263d7c83abe6f1309a64af3285a683c1b7672269`. Qualify the actual
  installed package and new native output independently of retained epochs.
- Keep the original fifteen safeguards separate from the person-specific review
  conditions and residual-profile order. The constructed procedures test their
  declared premises; a passing result is no institutional legitimacy score.
- Preserve source roles, original offsets, copy/edition distinctions and exact
  denominators. A count, imported source, checksum or automated extraction adds
  no reading credit and supplies no new scholarly acceptance.
- Write new runs to unused directories, with completion receipts written last.
  Keep prior failures, analytical producers, source pins and independent
  verdicts intact. Revalidate changed inputs instead of relabelling an old pass.
- Before delivery, bind the actual code, dependency, manuscript and output
  identities; qualify installed execution and rendered pages in their own
  scopes. Check tracked payloads, preserve provider expression locally, and
  verify the ordinary private-main push and remote head.

## Task closure

Close a task only after its stated output and acceptance evidence exist. Record
remaining uncertainty in [project status](docs/PROJECT_STATUS.md), with inputs,
responsibility and a checkable next action. Keep editorial feedback, specialist
criticism, real-browser behavior, copy collation and rights clearance separate
from completed software and rendering work.
